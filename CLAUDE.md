# SlotSettingAnalyzer

Android app (Kotlin, Room, Hilt) for logging pachislot (パチスロ) play sessions and estimating
machine settings from public reference data.

## Machine data catalog — naming convention

`app/src/main/assets/machines/*.json` is the live machine catalog. It's read directly by
`LocalAssetMachineMasterSource` (file listing, not the manifest/master files — see below).

**When adding a new machine:**
1. **File name = descriptive romanized snake_case slug** reflecting the machine's actual title,
   e.g. `tensei_slime.json`, `hokuto_tensei_2.json`. **Never** use a generic placeholder pattern
   like `dmm_slot_042.json` or `list_slot_017.json` — those are meaningless once a catalog grows
   past a handful of entries, and this project spent a full session (2026-08) undoing 74 files
   named that way.
2. The `machine.id` field inside the JSON **must exactly match the filename** (without `.json`).
   A mismatch here silently breaks anything that looks a machine up by id (play sessions, history).
3. For sequels/versions, suffix consistently with how the original is named (`_2`, `_v`, `_gou`, etc.).
4. **Before adding a new machine, check it isn't already covered under a different slug.**
   Duplicate entries for the same real machine happened repeatedly in this catalog's history —
   run `scripts/audit_machines.ps1` (see below) and check both the exact/normalized-name-collision
   sections and, if the new entry will have a `dmmUrl`/`ichigekiUrl`, grep the catalog for that
   same URL first.
5. Prefer filling `dmmUrl` (p-town.dmm.com) and `ichigekiUrl` (1geki.jp) with a real, verified
   page for that exact machine — not a top-page/index/syllabary-listing URL, and not a URL
   copy-pasted from a similarly-named but different machine (this has happened: wrong predecessor
   version, wrong smart-slot/normal-slot variant). Verify the page's title actually matches before
   committing.
6. Don't trust `manufacturer`/`releaseDate` values without a source — this catalog was originally
   bulk-generated by an AI assistant, and roughly a third of entries had wrong values (see
   `reports/machine_existence_verification_wave1_2026-08-04.md` and `wave2_2026-08-05.md`).

**Audit tool**: `scripts/audit_machines.ps1` (run via `& .\scripts\audit_machines.ps1` from the
repo root, PowerShell) scans the whole catalog for broken JSON, filename/id mismatches, duplicate
ids/names, missing or bare reference URLs, and any leftover generic-placeholder filenames. Run it
after any bulk edit to the machine catalog and check `reports/machine_audit_report_<date>.md`.

## Known parallel data store (do not assume it's live)

`app/src/main/assets/master/machine_details/*.json` and `app/src/main/assets/master/machines.json`
are a **separate, largely unused mirror** of the same catalog, intended for a remote-sync path
(`MasterApi`/`MasterSyncRepositoryImpl`) that the app doesn't currently exercise at runtime — the
actual data source is `assets/machines/` via `LocalAssetMachineMasterSource`. This mirror is known
to drift out of sync with the real catalog (stale/orphaned entries, entries with no corresponding
file). Don't treat it as a second source of truth without checking against `assets/machines/`
first.
